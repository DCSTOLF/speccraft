## 2026-09-28 — Bounding the reviewer payload: tiered context, a pre-dispatch byte budget, and ONE byte-producing owner (spec 0052, closed; **shipped in 1.18.0**)

**Spec:** specs/0052-review-prompt-size-budget/ (`related-specs: 0014, 0024, 0035, 0039, 0050`; `domains: external-tool-boundaries, spec-lifecycle`). Field report from tessera-cdc, 2026-09-25, after ~100 closed specs: `/speccraft:spec:review` composed **622 KB per reviewer** (`conventions.md` 339 KB, `architecture.md` 227 KB — 100 KB and 33 KB six weeks earlier), `claude-p` was registered `input = "argv"`, and the reviews **timed out at 600 s**. Hand-condensing both memory files got it to 121 KB — **still over the ~70 KB argv working limit**, because `spec.md` plus `guardrails.md` alone are ~50 KB. **Compaction alone does not fix this**, and that is the whole argument for the boundary belonging to the review command rather than to the memory files: `.speccraft/` only ever grows, every `spec:close` appends to it, and nothing shrinks it, so any fix expressed as "keep the files small" has a deadline.

**Why the old shape failed badly rather than gracefully.** A 600 s timeout is the least informative outcome available: ten minutes per agent, no verdict, and no way to distinguish "the model is slow" from "the prompt never fit". Worse, at the quorum layer it is **indistinguishable from an agent that simply had nothing to say** — so a review could reach quorum having consulted fewer models than the developer believed. Spec 0035 already ruled that a timeout is not a verdict; an over-budget agent had to be held to the same standard or the quorum was a lie by omission. **This repo was already exposed, not hypothetically:** `conventions.md` is 121 KB and `architecture.md` 39 KB here, and this spec's own six review rounds composed 185 KB → 209 KB, growing **24 KB across five rounds purely because the spec under review got longer**. By round 5 it had passed its own `REVIEW_MAX_PAYLOAD_BYTES` derivation basis — the spec would refuse itself under the rule it proposes, which is exactly what the raise-me protocol exists for. It succeeded only because this repo had hand-patched its own `agents.toml` to `stdin`; the shipped template had not.

**Decision: exploit the size asymmetry, and bound the bytes BEFORE dispatch.** Exactly the five files sent today are classified — **nothing is added to what a reviewer sees**, and `history.md` is deliberately an ERROR rather than an addition, because expanding the payload inside a spec about bounding the payload is scope creep with a straight face. **INLINE** (pasted, as today): the spec content, `guardrails.md`, `index.md` — small, and guardrails must be unmissable. **REFERENCE** (`architecture.md`, `conventions.md`): a repo-relative path, a byte size, and a `^##`/`^###` heading index. The asymmetry is 121,256 bytes versus a 3,063-byte index; a reviewer handed the path reads exactly the sections it needs with its own tools at ~1/40th the cost, and — unlike pre-selection done by the command — **cannot be cut off from a section the excerpting failed to anticipate**. Section-scoped excerpting was rejected for precisely that reason: a heading-match heuristic that misses a section means a guardrail the reviewer never saw, and the failure is silent. Tier membership is a **fixed table by identity**, not a size threshold, so the payload's shape cannot drift with the day's file sizes; classification resolves against `speccraft-state find-root` on the **full repo-relative path**, never the basename — otherwise `vendor/other/.speccraft/conventions.md` classifies as reference and a foreign file is silently admitted, or a spec document named `conventions.md` has its body silently omitted. Then two constants, each with its derivation in a comment beside it so a later contributor cannot raise it without confronting why it exists: `REVIEW_MAX_ARGV_BYTES=65536` (the field-reported ~70 KB rounded down to a power of two, and stated as a **conservative policy floor, not a guarantee of process creation** — real `ARG_MAX` is 128 KB–2 MB on Linux, 256 KB on macOS, and the environment block counts against it) and `REVIEW_MAX_PAYLOAD_BYTES=262144` (the next power of two above **197,238 bytes — the largest payload ever observed to complete against both shipped CLIs**, i.e. this spec's own round 3; a payload beyond the largest one ever seen to work is refused rather than attempted). Probing `getconf ARG_MAX` was rejected: the usable limit is not `ARG_MAX`, and a probe makes the refusal boundary vary by machine, so a review that refuses in CI would pass locally. An auto-fallback from `argv` to `stdin` was rejected too — it diverges from the configured contract for a CLI that genuinely needs argv, and converts a legible refusal into a silent behavior change. Refusal is **per agent**, and names the agent, its mode, the measured bytes, the limit hit **from the runtime effective value** (so the diagnostic cannot disagree with the behavior when an override is in play), the inline files ranked by size, and a remedy **specific to the limit** — stdin fixes an argv-limit refusal and does **nothing** for a payload-limit one, which needs compaction or a shorter spec. When both bite, both are named, worded so the argv limit cannot be misread as an available remedy.

**`review.lib.sh` becomes the SOLE byte-producing owner, and that forced a change to `aux-delegator`.** One composer, `review_compose_payload`, serves the full round **and** the spec-0035 scoped `--diff` round, so there is one place that decides what bytes are sent and therefore **one thing the budget can measure**. Left alone, `aux-delegator` would have composed a second time — re-prefixing the template, re-inlining context, and for `input = "file"` writing a *second* copy — so the bytes measured would not be the bytes dispatched, and the materialize-once rule would be violated **by the component furthest from the check**. It is now a pure dispatcher for review rounds, given `payload_file` + `input_mode` + `cwd`, forbidden from re-prefixing, re-inlining, or copying; `implement` and `analyze` are asserted **byte-identical to today**, not merely described as unchanged. The measured-equals-dispatched claim is by construction, not convention: the composer writes to **stdout** and the driver redirects that stream **once** into a single mode-`0600` artifact in the round's temp dir, because `bytes="$(compose)"` strips trailing newlines and the count would then describe bytes nobody sends. `review_materialize_payload` **refuses** an artifact that already exists; `file`-mode dispatch passes the round's own artifact rather than writing a tempfile (the most natural place for a second copy to appear); and the file→argv conversion uses `IFS= read -r -d ''` because reading into a variable for argv would reintroduce the identical newline strip **one step later**. No debug or convenience copy is permitted anywhere: a cached full prompt would restore the unbounded artifact by a side channel while the budget check still reported success.

**The attestation went through a wrong answer to get to the right one, and the right one is deliberately weak.** The reference tier has a prerequisite the first draft left unstated: handing a reviewer a path only works if the dispatched process starts in the right repository *and* can open files. If it cannot, the reviewer critiques a file it never read and returns a plausible verdict — **worse than the timeout it replaces**, because a timeout is at least legible. Draft 3 proposed a **read sentinel** the reviewer echoes back; round 3 correctly killed it, because the sentinel is *in the prompt*, so echoing it proves only that the reviewer read the prompt. It would have attested nothing while reading as though it did — the same silent-plausibility failure the tier itself risks. The replacement is a **content digest the reviewer computes**, with the expected value withheld from the payload and carried out-of-band on `--digest-out`; a digest cannot be produced without reading the bytes. Round 4 then killed the snapshot-and-dispatch-against-the-copy variant: it gave every reference **two identities** (the path named versus the path read) and made access depend on a temp location a sandboxed CLI may not open. So the digest is over the **live** file, and the residual TOCTOU window is seconds wide and **fails safe** — a mismatch means the verdict is not counted, the same outcome as an unread reference. **What it proves is stated and no more:** that a process with filesystem access at the dispatched cwd obtained the bytes. It does **not** prove the model incorporated them; a reviewer could checksum a path without ever bringing the content into context. The guarantee is deliberately the weaker one, because it converts "this agent cannot read files at all and nobody noticed" from an invisible failure into a mechanical one, which is the failure actually reported from the field. Claiming more would have been the sentinel again in a better costume. And the primitive is portable by construction — `shasum -a 256` preferred, pinned on **both** polarities — because `sha256sum` is GNU-only and this repo lost eight consecutive CI runs to that exact class (spec 0050) while the `awk` trap was being guarded carefully two functions away.

**Two predicates, not one, and the ordering consequence nobody had named.** `review_quorum` counts **agreeing** agents; conflating that with "did every reviewer answer" would break the `changes-requested` path, which must still persist a review. So `responses_complete` (every required reviewer returned a verdict — refusals, timeouts, failures and attestation failures are not verdicts) gates synthesis, the `review.md` write and the `reviewed_sha256` commit **for any verdict including `changes-requested`** (spec 0035 AC2, unchanged); `approval_quorum_met` **alone** gates `status: reviewed`. When `responses_complete` is false the round is **inert** — no `cross-reviewer`, no `review.md` write or replace, no fingerprint, no snapshot rewrite, status stays `draft`, and the report names every refusal *and* every verdict obtained, because a report naming only failures hides a real verdict while one naming only verdicts hides that the round consulted fewer models than it appears to have. That is what stops a refusal-only round wiping the prior `review.md` and collapsing spec 0035's provenance gate on the next `--diff`. AC24 followed from it: `review-diff --promote` used to rewrite `review-snapshot.md` at the **start** of a round, before any verdict existed, mutating the very anchor the inert-round rule requires unchanged — so an all-refused round would silently re-baseline and the **following** round would misclassify. The promote moved to `review_finalize_round`, which re-checks the completeness gate itself so a durable write cannot happen behind the runbook's back.

## 2026-09-26 — Release 1.17.0: the four-spec bump backlog, and why the release could not ship until CI was green (spec 0051)

**Spec:** specs/0051-release-1-17-0/ (status: closed; `related-specs: 0047, 0048, 0049, 0050`; `domains: release-pipeline`). A release-only spec carrying `1.16.0 → 1.17.0` for **four** specs that closed without a bump. **Minor, not patch:** four new subcommands (`tasks-verify`, `build-repair-log`, `design-fingerprint`, `set-status --kind`), a new guard behaviour (build-repair mode), three new `state.json` session keys; no existing caller contract changed.

**Why four accumulated.** `bump-before-close` exists precisely to prevent this, and each deferral was individually defensible: 0047 shipped mid-arc, 0048 and 0049 explicitly deferred to "a later release spec carrying them together", and 0050 was emergency CI repair. They compounded anyway. **But the binding constraint was CI, not discipline:** `auto-tag` → `release.yml` → `verify-release.sh` fires on push to `main`, so any bump pushed during runs #79–#86 would have tagged and published from a tree whose own suite was failing on three jobs. Run #89 (spec 0050) was the first green since #78 on 2026-08-04, and that is what made this releasable. The right reading of the backlog is therefore "the release gate was correctly closed", not "four specs were sloppy" — though the convention still deserves teeth, and two candidate mechanisms are recorded in the changelog rather than chosen here.

**The eight locations, and why a bump is a real RED→GREEN cycle.** 3 Go `const version`; 4 grep/const oracles (the three sibling `version_test.go` plus `manifest_version_test.go`); 2 JSON manifests. Each oracle's function name ENCODES the version, so the bump renames it — registering a fresh red-candidate under the TDD guard, which a bare const edit could never do — and each carries a NEGATIVE check advanced to reject the outgoing version, so a half-applied bump fails rather than passing on the new value alone. `bin/` was rebuilt and `.binary-version` re-stamped in the same task: skipping that leaves this repo's own hooks running 1.16.0 binaries against a 1.17.0 manifest, at which point `install-binaries.sh` tries to download a release that does not exist yet — the spec-0050 staleness class, self-inflicted.

**Decision: the bump and the close are SEPARATE commits.** The close-commit invariant (spec 0008) requires `changelog.md` and the `status:` flip in one commit; it does not require the bump to join them. Splitting let the changelog record what the release pipeline and CI ACTUALLY reported about the tagged commit instead of an intention — closing alongside the bump would have meant asserting AC6 (a verified published release) and AC7 (CI green on the bump commit) before either could be observed, which is exactly the "a bump is not done when the consts are edited" failure spec 0021 exists to prevent.

**Verified end to end.** `v1.17.0` tagged at `bdefb29` by `auto-tag` via `RELEASE_TAG_PAT`; `Release` run 19 success; 4 platform tarballs + `checksums.txt`; `scripts/verify-release.sh 1.17.0` OK strong-form (every tarball downloaded, SHA-256 recomputed, all matched); CI run **#92** green on all seven jobs. Plus a check hash verification cannot make: the PUBLISHED binaries were extracted and run — all three report `1.17.0` and both `tasks-verify` and `design-fingerprint` dispatch. That is not ceremony. The defect behind eight red runs was an installed plugin downloading a release whose binaries lacked `tasks-verify`; proving the v1.17.0 bytes answer the new subcommands closes that loop at the DISTRIBUTION end, where hash-only verification would have passed a correctly-packaged wrong build.

**Divergence (honest), and it is all about predicates.** (1) **T1 and AC3 were both wrong on first writing, identically:** they asserted the ABSENCE of `1.16.0` from files whose stale-version negative checks must contain it, and from `ci.yml`/`run.sh` comments that legitimately narrate spec 0050's clobber. For a value being REPLACED the invariant is **polarity** — positive expectation names the new, negative check names the old — not absence. AC3 was rewritten to say so; the alternative was padding the predicate with `grep -v` exclusions until it asserted nothing. **Third occurrence of that shape in one session.** (2) **T6 depended on ambient `PATH` and failed at close having passed during implementation** — the only difference being a hand-typed `PATH="$PWD/bin:$PATH"` on the earlier runs. Without it the cached installed plugin (1.11.0, no `--kind`) shadows the repo's binary and four spec-0049 tests fail environmentally. T6 now sets `PATH` itself; **spec 0050's T7/T12/T15 carry the same latent flaw and passed by the same accident**, and being closed and immutable they are recorded rather than fixed. An oracle whose verdict depends on the caller's shell is not an oracle. Both rules are now in `conventions.md`. (3) `memory-keeper` was not invoked (standing instruction against unbidden subagents); changelog and this entry written directly.

**Still open after this release:** probers for Python/JS/TS, so the spec-0048 guard wedge is live in those languages; `TrackEdit` keys `edited_test_files`/`edited_prod_files` with a bare `filepath.Abs`, leaving spec 0048 AC15's "every state key this package writes" not literally true — the same shape as the bug that cost 25 macOS test failures, harmless only because nothing reads those lists through the normalizer; the aux-delegator false-quorum hazard from the 2026-08 field report; whether a source-built `bin/` should ever be overwritten by a release of the same version; and history compaction (14 entries), explicitly deferred.

## 2026-09-26 — CI green again: six defects behind eight red runs, three of them one root cause (spec 0050)

**Spec:** specs/0050-ci-green-again/ (status: closed; `related-specs: 0018, 0047, 0048, 0049`; `domains: tdd-guard, cross-env-portability`). CI on `main` had been red for **eight consecutive runs** (#79-#86); the last green was #78 on 2026-08-04, and run **#89** is the first green since. Every defect had been green locally, which is the fact worth keeping: the devcontainer suite is not a proxy for CI, and four of the six were only observable once something else was fixed.

**Defect A — a state key written by one spelling and read by another.** Spec 0048's AC15 called `NormalizeStateKey` "the single canonical path normalizer for every state key this package writes". `SetRedCandidates` did not apply it: it stored `s.Session.RedCandidates[file]` verbatim, trusting callers, while `siblingRedCheck` reads that map through `redCand[NormalizeStateKey(sib)]`. A caller passing a merely-absolute path therefore wrote a key the reader could never find, and the guard answered **"No test was added this session"** for a session that had added one — the exact refusal spec 0048 existed to remove, back through a different door. Invisible on Linux; on macOS `t.TempDir()` returns `/var/folders/…`, a symlink to `/private/var/folders/…`, and **25 guard tests failed there while passing here**. Fixed at the **writer**, because `CaptureRedCandidates` already normalized and a per-call-site fix leaves the trap armed for the next caller. The diagnosis technique generalises and is now a task-level pin (AC4): pointing `TMPDIR` at a symlink reproduces all 25 failures **on Linux**, byte-for-byte the same set.

**Defect B — the SessionStart hook installs release binaries over freshly built ones — and it did this to THREE different consumers.** `install-binaries.sh` finds no `.binary-version` stamp (gitignored, hence absent on every fresh checkout), so it DOWNLOADS the last release and untars it over `bin/`. (1) `session-start.bats` runs the real hook against the real plugin root, so the Linux bats job's freshly built binaries were replaced mid-suite; that file sorts before `tasks-verify.bats`, so four tests failed with `unknown subcommand: tasks-verify` — a subcommand that exists at HEAD and not in v1.16.0. (2) The macOS bats job, identically. (3) **The E2E devcontainer job**, where `--plugin-dir` loads HEAD's commands, hooks and skills while the binaries they shell out to came from the release — so the suite validated HEAD's markdown against release Go, and `/speccraft:spec:close` step 2's `tasks-verify` call degraded to the agent running each `done:` predicate by hand. The clobber is **as old as those tests** and was harmless only while no test needed a subcommand newer than the last release; the first unreleased subcommand turned a long-standing latent fault into a red main. Fixed by stamping the version (derived from `plugin.json`, never a literal) in both bats jobs and in `run.sh` before the lifecycle, and by pinning `SPECCRAFT_RELEASE_BASE` at an unreachable `file://` base in the suite so a developer's `bin/` cannot be made older than its source either. **The three symptoms looked unrelated and were one bug.**

**Defect C — a BSD tool advertising GNU compatibility read as a GNU build.** `scripts/assert-no-gnu-userland.sh` (spec 0049 AC10) rejected any required tool whose `--version` output contained `GNU`, on the premise that BSD tools reject `--version`. **They do not.** macos-14's `/usr/bin/grep` accepts it and answers `grep (BSD grep, GNU compatible) 2.6.0-FreeBSD`. The substring matched, the assertion failed the `hooks-macos` job **before bats ran**, and so **the macOS suite had never once executed** — which is worse than the GNU-greened job AC10 was written to prevent, because it yields no signal in either direction rather than a false one. The probe now asks whether the tool **names itself** a GNU implementation: `(GNU ` or a line-leading `GNU `, the second alternative load-bearing because gawk prints `GNU Awk 5.1.0` with no parenthesis and a paren-only pattern would admit the commonest GNU awk. Compatibility CLAIMS are stripped before the test, explicitly, so a future BSD tool printing `(GNU compatible)` with no `BSD` prefix cannot re-open the hole. The fixture's real failure was modelling BSD tools as *rejecting* `--version`; it now models the actual macOS strings for `grep` and `awk` alongside the rejecting shape, since both exist.

**Defects D and E — what the macOS suite found on its first run.** It ran 339 tests and failed 11, in two clusters, **both shipped defects of exactly the class spec 0049 was written to catch, and both under a surface the portability meta-guard scans.** (D) `hooks/pre-tool-use.sh` canonicalised with `realpath -m`; macOS ships `realpath` **without** `-m`, so the call failed under `set -e` and the hook exited **before delegating to `speccraft-guard`** — meaning the `state.json` single-writer guard **and the entire TDD invariant** were inert on macOS, reporting `realpath: illegal option -- m` in place of either guard's message. Replaced with pure-shell `canon_path`, splitting by parameter expansion rather than `dirname`/`basename` (this runs on every write tool call, and relying on BSD's positional-operand tools to accept `--` is the same class of assumption as the defect being fixed). Dropping `-m` is safe by argument, not by luck: only the **directory** need exist, and when it does not, the target cannot be `<root>/.speccraft/state.json`, whose directory always exists because `ROOT` was found by locating it. (E) `commands/sync.lib.sh` piped `reconcile` into the GNU-only coreutils checksum tool, killing `sync_design_fingerprint` and every caller including `sync_consolidate_design`. It now **delegates** to a new `speccraft-state design-fingerprint`, exposing the `designFingerprint` helper Go already used for `ledger-archive --expect`. Delegation over a `command -v` shim deliberately: the shell copy was a second implementation of one number, and a fingerprint whose two producers can drift defeats its own purpose.

**Defect F — the E2E's non-deterministic symptom.** Given (B3), `close.md` step 2's gate was executed by an LLM by hand. The `[10/13]` prompt said nothing about what to do on violations, so the run's outcome depended on whether the `done:` predicates the agent authored at step 8 still matched the code it wrote at step 9. **Twice they did not** — a test renamed by a refactor; a `grep -v '^\./main.go$'` filter defeated by a path printed without `./` — and the agent, facing a gate whose bypass needs a token the prompt never supplied, **correctly stopped for a decision**. The suite then failed at `exists changelog.md`, blaming close for a stale locator three steps upstream. #86 passed with the identical bug purely because that judgement went the other way. The prompt now resolves it the way close.md's own option (a) does — reconcile a stale LOCATOR, re-run, continue — and deliberately does **not** supply `SKIP-TASKS-VERIFY`, because bypassing would stop exercising the gate at all; weakening a predicate stays forbidden, so the work must still be done AND provable.

**Extending a meta-guard revealed the clause was mis-scoped.** Adding the checksum tool to the portability guard flagged a **pre-existing, correct** Go comment in `ledger_archive_cmd.go` documenting the shell equivalent of a value that file computes properly in Go. Both new forms are dangerous only as SHELL invocations — Go reaches sha256 via `crypto/sha256` and paths via `path/filepath` — and the one shape Go could commit, `exec.Command("sha256sum", …)`, is already outside this guard by its own stated limit and covered by the macOS Go runner. The clause therefore excludes `*.go`, **pinned by a fixture** rather than left implicit. A guard that fires on prose about a defect, in a language that cannot commit it, trains readers to weaken guards — which is the opposite of what it is for.

**A correction to my own reasoning, recorded because it nearly misled the diagnosis.** I read the bats log's truncated `usage()` dump — stopping at spec 0044's subcommands — as evidence that a release binary had replaced the built one. A new usage/dispatch parity test showed that inference was unsound: `tasks-verify`, `review-commit` and `build-repair-log` were **missing from `usage()` at HEAD too**, so a current binary produced the same dump. ## 2026-08-04 — Release 1.16.0: ledger write-locking closes the concurrent-writer race (spec 0045)

**Spec:** specs/0045-ledger/ (status: closed; `related-specs: 0043, 0044`). Specs 0043 (workspace ledger/membership reconciliation) and 0044 (design consolidation + ledger-row archival) both shipped under an explicit **single-writer assumption** and *bounded-but-deferred* the residual concurrent-writer race: every ledger writer (`ledger-set`, `ledger-archive`, the conductor) does read → modify → atomic-rename with no mutual exclusion, so two writers reading the same bytes could each rename and the last silently clobbers the first's change. `ledger-archive --expect` closed the caller→op handoff but NOT the op's own read→rename window — it is not a filesystem CAS. As the conductor and `/speccraft:sync` run more autonomously, concurrent ledger writes become plausible, and a lost update to the ledger is a silent correctness failure. 0045 is the load-bearing concurrency fix only; two adjacent follow-ups (`/speccraft:sync --recursive` and `ledger.archive.md` compaction) were **split into their own specs**.
**Decision:** Serialize **every** ledger writer's *entire* transaction behind a host-level exclusive advisory `syscall.Flock(LOCK_EX)` on a sidecar `<workspace-root>/.speccraft/ledger.lock` (path via `FindWorkspaceRoot` so the lock always lands at the workspace root, never a member repo), and move each writer's **authoritative read inside the lock** so read → in-memory transform → atomic rename is one indivisible critical section. `ledger-archive`'s two-file transaction is held under the **same** lock end to end (both-present crash recovery → archive append+rename → live-ledger remove+rename → every error path). The `--expect` CAS is kept as a **semantic** check on the existing `reconcile | sha256sum` fingerprint but now re-derived from the ledger bytes read *under the lock* and compared before any write — an **in-process** computation (never a shell-out from inside the critical section) equal to what the pipeline would yield; no whole-ledger byte-identity claim is made (a reconcile projection cannot establish that). `ledger-set` intentionally takes no `--expect`: single-field write, serialization suffices, last-writer-wins on the same field is deliberate. New portable core `tools/cmd/speccraft-state/ledger_lock.go` (`withLedgerLock`, `parseLockTimeout`, the `ledgerLockHold` test seam) + a build-tag split (`ledger_flock_unix.go` for shipped linux+macOS, `ledger_flock_other.go` stub that fails loud on any non-unix build). Bound mechanism is a **`LOCK_NB` poll loop** (10ms interval), NOT a cancellation goroutine — chosen consciously because the poll loop cannot leak a late acquisition after `ledger busy` was already returned (codex S1). Timeout via `SPECCRAFT_LEDGER_LOCK_TIMEOUT` (Go duration; default `10s`; unset/empty/invalid/zero/negative → 10s fallback, codex S2); on contention beyond the deadline the writer exits non-zero and stderr **contains** `ledger busy` (substring, never exact-equality — claude-p S1). Crash-safe by construction: advisory, kernel-released on exit, so on-success/on-error/on-crash are the same exit clause and no stale lock ever wedges the next writer. Happy-path byte-identity of `ledger.md` / `ledger.archive.md` is preserved (the only new on-disk artifact is the ignored `ledger.lock` sidecar).
