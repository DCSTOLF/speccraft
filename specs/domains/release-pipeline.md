# Domain: release-pipeline

Distribution: GitHub-Release binary publishing, tag-on-version-bump automation, `install-binaries.sh` download/fallback, doctor provenance, release-completeness verification.

- Helper binaries ship only as GitHub Release assets (never committed): `release.yml` triggers on `v*` tags and publishes exactly the four tarballs `speccraft-<version>-{linux-amd64,linux-arm64,macos-amd64,macos-arm64}.tar.gz` plus `checksums.txt` on a published (non-draft) release (spec 0021)
- A `main`-push CI job auto-creates and pushes the `vX.Y.Z` tag matching `.claude-plugin/plugin.json` when none exists, using a PAT/deploy key (never `GITHUB_TOKEN`, whose loop-guard suppresses tag re-triggers) so `release.yml` fires; completeness is only ever asserted against an existing tag, never bare `plugin.json`, keeping the pipeline deadlock-free (spec 0021)
- `scripts/verify-release.sh <version>` runs as the final `release.yml` step and is reused by the completeness guard: it asserts HTTP 200 on the four tarballs + `checksums.txt` and recomputes each tarball's SHA-256 against `checksums.txt`, failing the release loudly on any partial or broken publish (spec 0021)
- `install-binaries.sh` installs via download without Go when a release exists (checksum-verified) and writes `.binary-provenance=download`; on download failure it prints a stderr warning naming the failed URL before falling back to `go build`, writes `.binary-provenance=source`, and `doctor.sh` reports that as a distinct "built from source (download unavailable)" state (spec 0021)
- The release base URL is overridable via `SPECCRAFT_RELEASE_BASE` for hermetic, network-free install/checksum/failure fixture tests, and producer and consumer agree on `checksums.txt` (not `checksums-merged.txt`) as the published checksum asset name (spec 0021)
- A version bump touches EIGHT locations: 3 Go `const version` (`tools/cmd/speccraft-{state,guard,drift}/main.go`), 4 grep/const oracles (the three sibling `version_test.go` plus `tools/internal/speccraft/manifest_version_test.go`), and 2 JSON manifests (`.claude-plugin/{plugin,marketplace}.json`). Each oracle's FUNCTION NAME encodes the version, so a bump RENAMES it — which is what registers a fresh red-candidate under the TDD guard, something a bare `const` edit can never do — and each carries a NEGATIVE check advanced to reject the OUTGOING version, so a half-applied bump fails instead of passing on the new value alone (specs 0019/0046, generalised by spec 0051)
- The bump must also rebuild `./bin/` and re-stamp `.binary-version`, in the same task. `install-binaries.sh` keys its fast path on an exact stamp match against `plugin.json`, so a bumped manifest beside unbumped binaries makes this repo's own hooks try to DOWNLOAD a release that does not exist yet — the spec-0050 staleness class, self-inflicted. A bump is also the mechanism by which installed plugins pick up new binaries, which is why a release carrying new subcommands is MINOR and not patch (spec 0051)
- The version bump and the `spec:close` are SEPARATE commits. The close-commit invariant (spec 0008) binds `changelog.md` to the `status:` flip; it does NOT require the bump to join them. Splitting is load-bearing: a release's own ACs include a verified published release and CI green on the bump commit, and neither can be OBSERVED until after the push. Closing alongside the bump means asserting them in advance — exactly the "a bump is not done when the consts are edited" failure spec 0021 exists to prevent. Bump while in-progress, push, verify, then close with the real tag/run/asset evidence in the changelog (spec 0051)
- Strong-form hash verification is NECESSARY BUT NOT SUFFICIENT: after `verify-release.sh` passes, EXTRACT a published tarball and RUN the binaries — assert the version they report and that subcommands added since the previous release actually dispatch. `verify-release.sh` proves the published bytes match `checksums.txt`; it cannot detect a correctly-packaged WRONG build. That gap is not hypothetical: the defect behind eight consecutive red CI runs was an installed plugin downloading a release whose binaries lacked `tasks-verify`, and hashes over those tarballs would have verified perfectly (spec 0051)
