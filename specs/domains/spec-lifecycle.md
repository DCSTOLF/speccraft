# Domain: spec-lifecycle

Spec lifecycle commands and their gating: `spec:revise` status gates, artifact archival, `revision:` counter, spec-reviser subagent, code cross-check.

- `/speccraft:spec:revise` operates on the active spec only, gated to source status `draft|reviewed|planned` (rejecting `in-progress`/`closed`/`archived` with a status-naming error) and errors when `active_spec` is empty (spec 0015)
- On a real spec.md edit, revise increments the `revision: N` frontmatter counter (inserting `revision: 0` if absent — command-owned, never agent-owned), archives stale downstream artifacts by renaming `review.md`/`plan.md`/`tasks.md` to `*-r<N_old>.md` per source status, and resets status to `draft`; a whitespace/newline-only edit is a no-op that changes nothing and prints `no changes — spec unchanged` (spec 0015)
- Revise's optional code cross-check greps identifier tokens found in backtick spans (regex `[A-Za-z_][A-Za-z0-9_]{3,}`) within `## What`/`## Acceptance criteria`/`## Out of scope` across `packages[]` using portable `find`/`grep` (never ripgrep); zero-match tokens become `^Q-DRIFT:`-prefixed re-interview questions, and an empty `packages[]` prints `packages[] empty — skipping code cross-check` and proceeds (spec 0015)
- The `spec-reviser` subagent (`tools: [Read, Write, Edit, Bash]`, no `Agent` tool) re-runs the Socratic interview against existing spec.md content and must not modify the command-owned frontmatter keys `revision:`/`status:`/`id:`/`created:` (spec 0015)
- Revise preflights before any mutation: it aborts (modifying nothing, not invoking the reviser) when a required source artifact for the source status is missing — the old `*-r<N>.md` archive-collision refusal (`preflight_archive_collisions`) is removed in favor of spec 0036's self-healing ordinal selection (spec 0015)
- Planning/execution authoring prose (`tdd-planner.md`, `spec:{plan,implement,delegate}.md`) and the shipped `templates/speccraft/conventions.md` are stack-agnostic: they reference the project's `speccraft-state test-command` / conventions.md value rather than Go idioms, with a concrete language test command allowed only under a labeled `Example`; two meta-tests enforce both the prose rule and the template's freedom from language-specific `enforce:` regexes and idioms (`fmt.Errorf`, `slog`, `*_test.go`) (spec 0034)
- `/speccraft:spec:review --diff` runs a diff-focused re-review: `speccraft-state review-snapshot write` freezes `spec.md`, and `review-diff` emits a versioned JSON envelope (`snapshot`/`changed`/`changed_sections`/`diff`/`fingerprint`/`base_fingerprint`) from a section-anchored textual diff keyed by `##` heading + ordinal (byte-identical bodies never reported). The round-start call is READ-ONLY: spec 0052 removed `--promote` from it and deferred the snapshot promote to `review_finalize_round`, because promoting before any verdict existed rewrote the very anchor an inert round must leave byte-identical — so an all-refused round silently re-baselined and the next `--diff` misclassified. The reviewer-visible spec content now comes from the round temp dir's frozen spec image, read once; the composer reads only the `<spec-src>` path it is handed, so the single-read transaction was never tied to the file name (spec 0035, amended by spec 0052)
- The command classifies via a provenance gate on the prior `review.md`'s `reviewed_sha256` vs the envelope `base_fingerprint`: byte-identical → short-circuit (no reviewers); baseline-not-last-reviewed or first review → full review with a warning; else scoped re-review of the changed sections plus a regression sweep over previously-approved criteria (`templates/prompts/re-review.md`). A scoped round's payload MUST carry the prior `review.md` inline: without it the reviewer gets no previous findings and cannot judge whether a change resolved them, and a full-round compose recipe omits it SILENTLY — no error, just a worse review. That exact omission shipped twice, once after spec 0035 and again in spec 0054's runbook, so the attachment is asserted rather than described (spec 0035, amended by spec 0054)
- `review.md` records the reviewed `spec.md` fingerprint (sha256 of raw bytes) as one `reviewed_sha256:` line via a single atomic temp-then-rename commit, written only when `review_responses_complete` holds — every required reviewer returned a verdict — and then for ANY verdict including `changes-requested`; nothing is written on any failure, and an inert round leaves the prior `review.md` byte-identical. `review-snapshot.md` persists under `specs/`, outside the `speccraft-drift` scan scope. `review_finalize_round` takes an optional 4th argument `<kind>` over the closed set `spec design brief code`, defaulting to `spec` so spec-0052's finalize tests pass unedited, and ONLY `spec` promotes the snapshot and stamps the fingerprint: `design` and `brief` write their own `review.md` (`design/<id>/`, `product/<id>/`) with no snapshot promote, no fingerprint, and `status: draft` even at quorum — `reviewed` is a spec-lane state, and a design is promoted by `/speccraft:arch:decide` and a brief by `/speccraft:pm:prioritize`, never by a review round — while `code` writes nothing durable and reports `n/a`, having no document and no lane. An unknown kind is exit 2 naming the word, NEVER a fall-through to `spec`, so a typo cannot earn a non-spec directory the spec lane's durable writes. Everything that can refuse is resolved BEFORE the first durable write, the vendor flag included: resolving it after the promote and the stamp left both written and then returned non-zero — a partially committed round that reads as a failed one (spec 0035, amended by specs 0052 and 0054)
- The revision counter and archived `*-r<N>.md` artifacts are reconciled by one authority model: `Effective = hasArchived ? max(fmRev, maxArchived+1) : fmRev` (frontmatter `revision:` is canonical; archives only heal it forward, never backward), surfaced by `ComputeRevisionState`, `speccraft-state effective-revision`, and the heal-only `reconcile-revision` (a no-op when the counter already leads) (spec 0036)
- Revise archiving is self-healing and no-clobber: it moves each disposable live artifact (`review.md`, plus `plan.md`/`tasks.md` for `planned` source) to `*-r<A>.md` at ordinal `A = Effective` (provably free) via a genuine no-replace primitive (`link(2)`-then-unlink, failing safe where unavailable, idempotent by inode identity across an interrupted move), never archives `spec.md`, then writes the counter to post-archive `Effective` and flips `status` to `draft` last — so a pre-existing `review-r<N>.md` can no longer deadlock revise (spec 0036)
- In-place draft edits intentionally keep the same `revision:` — a revision corresponds to a completed review cycle (an archive), not every edit — so the review→edit→re-review loop within one draft does not advance the counter (spec 0036)
- `tasks.md` carries an opt-in decomposition contract keyed by frontmatter `contract: done-means-v1` (versioned so grammar evolution takes a new value): a task is a checkbox at column 0 whose id may be dotted or multi-dot (`T0.1`, `T0.5.1`), a sub-checkbox is an *indented* checkbox whose id is its parent's id plus one `[A-Za-z0-9]+` segment (one level only — **indentation alone** makes a sub-checkbox), any indented bullet not matching that shape is prose ignored at any depth, and each task carries exactly one non-empty `done:` line indented exactly 2 spaces whose block ends at the next column-0 task, the next heading, or EOF (spec 0047)
- `speccraft-state tasks-verify <tasks.md> [--run|--help]` is the completion oracle — a `run()`-seam case in the cmd package, read-only, exiting `0` clean / `1` violations / `2` malformed, emitting findings as tab-separated `task-id`/`kind`/`detail` with `\t`/`\n`/`\r` escaped and `detail` capped at 4 KiB: a `[x]` parent with a `[ ]` sub-checkbox is a violation on **every** tasks.md (contract key or not), while the `done:` requirement applies only under the contract and then to every task regardless of tick state; malformed covers missing frontmatter, an orphan sub-checkbox, a duplicate task id, and an empty or duplicated `done:` or a bare `done: $` with no command (spec 0047)
- A `done:` value beginning with `$` is an executable predicate run only under `--run` and only for ticked tasks, under `/bin/sh -c` (POSIX, absolute path) from the repo root with inherited env and stdin `/dev/null`, output combined and captured, bounded by `SPECCRAFT_TASKS_VERIFY_TIMEOUT` (Go duration, default 30s; unset/empty/invalid/zero/negative → default) whose expiry kills the whole **process group** so a forked grandchild cannot hold the captured pipe open; any other `done:` value is prose that is never verified, and a predicate must never invoke the verifier that runs it. Execution is unix-only via a `tasks_predicate.go`/`tasks_predicate_other.go` build-tag pair whose non-unix half reports `predicate-unsupported` rather than silently reporting clean (spec 0047)
- `/speccraft:spec:close` step 2 is this mechanical gate — `tasks-verify --run`, run **before** the diff (step 3) and before `memory-keeper` (step 4) so a refused close does no downstream work — replacing the former eyeball check that only asked whether top-level boxes were `[x]`: exit `2` is a bug to hand-fix and is **never** bypassable, exit `1` is a decision whose bypass requires the literal token `SKIP-TASKS-VERIFY` (a blanket "approve all" or a non-interactive context does **not** qualify), and a bypass records the skipped findings verbatim in the spec's `changelog.md` under `## Skipped task verification`; the contract is pinned durably by `tests/hooks/close-gate.bats` rather than by a spec-local `done:` grep, which would stop executing the moment that spec closed (spec 0047)
- A review round has TWO separate predicates gating different things, because `review_quorum` counts AGREEING agents and conflating that with "did everyone answer" would forbid a legitimate `changes-requested` round from persisting its review: `review_responses_complete` (every required reviewer returned a verdict — a refusal, timeout, failure or failed attestation is not a verdict) gates synthesis, the `review.md` write and the `reviewed_sha256` commit for ANY verdict including `changes-requested`, while `review_approval_quorum_met` (agreeing verdicts >= quorum) ALONE gates `status: reviewed`. An unknown outcome token is an error rather than a silent non-verdict. A THIRD value is reported alongside them and GATES NOTHING: `single_vendor_approval`, true when every approval counted toward a met quorum shares the spec author's vendor, which makes the cross-model premise's weakening on the default path VISIBLE rather than impossible — the shipped template enables one Claude subagent at `review_quorum = 1`, so a Claude-authored spec can reach `status: reviewed` on one Claude reviewer's approval. Requiring a non-Claude approval instead would make a round unsatisfiable whenever the only non-Claude reviewer is unavailable — exactly the `codex-plugin-unavailable` path — turning a degraded reviewer into a hard block on the lifecycle, so quorum arithmetic is byte-identical with and without the flag. The flag is reported ONLY on a met quorum (operator ruling, 2026-11-24, overruling the opposite recommendation): it describes an approval the round ACTED ON, so printing it on a round that never reached quorum invites "approved, by one vendor" where the round was not approved at all. Vendor resolution is skipped along with the reporting, so a below-quorum round is never failed over a value nobody reads; with quorum met an unresolvable vendor IS fatal and still leaves the spec dir untouched. The per-verdict `mode`, requested `model` and `vendor` fields are NOT gated — they describe the verdicts obtained rather than the approval — and a capability reachable only by passing a new optional argument needs an assertion over the shipped CALL SITES, since this record switched on only with a 5th and 6th argument to `review_finalize_round` and shipped DEAD past nine spec-review rounds because not one of the nine call sites passed them (spec 0052, amended by spec 0054)
- When `responses_complete` is false the round is INERT: `cross-reviewer` is not invoked, `review.md` is neither written nor replaced, no fingerprint is committed, `review-snapshot.md` is not rewritten, status stays `draft`, and the report names every refusal AND every verdict obtained — a report naming only failures hides a real verdict, one naming only verdicts hides that the round consulted fewer models than it appears to have. `review_finalize_round` is the single place that promotes the snapshot and stamps the fingerprint and it re-checks the gate itself, so a durable write cannot happen behind the runbook prose (spec 0052)
- The review runbook is ONE file, `skills/review-round/SKILL.md`, referenced by all four review commands (`spec:review`, `spec:review-code`, `arch:review`, `pm:review`) — it lives under `skills/` and not `commands/` because every `.md` under `commands/` registers as a slash command and a runbook there would create a stray `/speccraft:spec:review-round`. Its order is create-round-dir -> pre-round tree snapshot -> source-lib -> compose -> materialize -> `review_budget_check` -> dispatch, pinned by a meta-test comparing FOUND MARKER INDICES rather than absolute line numbers: a budget check after dispatch would prevent nothing, since the payload has already reached the CLI, and a pre-round snapshot taken before the round dir exists would record the round's own setup as a reviewer write. Each agent gets a DISTINCT artifact path inside the round dir and the outputs are hash-compared by `review_hash_compare_outputs` — a helper since spec 0054, where 0052 left it as runbook prose — before verdicts are counted, because identical hashes across two agents are a dispatch bug rather than agreement, and neither verdict is counted when they match. Because a MODEL executes this markdown, the runbook's text IS the implementation and is checked like code: its fenced calls are compared against the real functions (with a premise row proving the function really does reject the wrong argument shape, or the pin is vacuous), and every `$VAR` in its `bash` fences must be assigned there or declared in the parameter table — an unset variable in such markdown is not an error, it expands to empty and the step quietly does the wrong thing. A proceed token is never a recordable outcome: a helper's `ok` means "continue" and storing it into the outcomes file hit the unknown-token arm and aborted every successful subagent round at its first predicate (spec 0052, amended by spec 0054)
- Compose → budget-check → dispatch → outcome-record → attestation is ONE round, shared by all four review commands and parameterized by the document under review, the inline set, the reference set and the template: `spec:review` reviews `specs/<id>/spec.md` into `specs/<id>/review.md` with the `--diff`/snapshot/fingerprint lane; `arch:review` reviews `design/<id>/design.md` into `design/<id>/review.md`; `pm:review` reviews `product/<id>/brief.md` into `product/<id>/review.md`; `spec:review-code` reviews ONE frozen diff plus the active spec if any, to stdout only. Before spec 0054, `arch:review` and `pm:review` said only that they used "the same multi-model backend `/speccraft:spec:review` uses, unchanged" with no runbook, so the model running them IMPROVISED dispatch, and `spec:review-code` looped "each enabled agent" through `aux-delegator` with no notion of mode, budget or attestation. `arch`/`pm` keep their critic-first stage and write `review.md` only on a COMPLETE round: an inert round leaves an existing one byte-unchanged (`cmp -s`) and creates none where none existed. `review-code` freezes its diff ONCE into the round dir (`git diff HEAD`, or `git diff <ref>...HEAD` with `--base`) and composes those same bytes into every reviewer's payload, so every mode reviews identical bytes; with no active spec it still runs and the payload says so. Untracked files are OUT of the reviewed diff, stated in the payload prose and repeated in the output rather than left as an implicit side effect: one frozen, reproducible, hashable diff is what makes attestation meaningful and `git diff HEAD` is exactly reproducible from the recorded `HEAD`, whereas a snapshot that also swept in untracked files would not be — the same objection this repo raises to a reviewer that collects a different change than the one speccraft composed and attested. Widening it (an `--include-untracked`) is out of scope (spec 0054)
- A review round owns a PERSISTENT directory, `<repo-root>/.speccraft/.review-rounds/<kind>-<id>-<unix-ts>-<rand>`, mode 0700, whose path is printed so the runbook can carry it across tool calls; `cli`, `acp`, `codex-plugin` and `subagent` all read from it. It is PUBLISHED ATOMICALLY WITH ITS LEASE: `review_round_dir_create <kind> <id> <timeout-s>` builds under `.building-<expiry-unix-ts>-<rand>` INSIDE `.review-rounds/` (already ignored, same filesystem, which is what makes the `mv` atomic), writes the `lease`, then renames — `mkdir` plus a separate lease write is two steps, and the sweep's "missing lease ⇒ reclaim" rule would turn the window between them into the deletion of a live round. Uniqueness comes from `mktemp -d` and an existing final path is refused before the `mv`, because a command-substitution subshell inherits the parent's `$RANDOM` under zsh and `$$-$RANDOM` names collided, nesting one round inside another with a 0 exit status while one round's cleanup deleted the other's payload. The BUILD EXPIRY IS IN THE NAME (`now + review_timeout_s + 300`, fixed at `mkdir` time before any fallible setup) so the most-likely-to-be-abandoned state is self-describing: a half-built dir has no lease to read, and a sweep that had to COMPUTE its threshold would have nowhere to get `review_timeout_s` from and no unambiguous answer with two concurrent rounds. SWEEPING IS LIVENESS-BASED, NEVER AGE-BASED: each round carries a `lease` holding an absolute expiry of `start + review_timeout_s + 300 s`, written ONCE and never re-stamped (there is deliberately no renewal helper; the load-bearing assertion is that a lease's expiry is byte-identical before and after a full round, which catches a re-stamp under any name), and `review_round_sweep` — which takes no age or `max-age` argument, so age alone can never drive a deletion — removes a round only when its lease has expired or is missing/unparseable, and reclaims a `.building-*` dir only once the expiry encoded in ITS OWN NAME has passed, read rather than recomputed, so two concurrent rounds with different timeouts are each judged by their own threshold. Every lifecycle path finishes inside the margin or is covered by quarantine, and a forward constraint follows: a future unbounded phase must bound itself or quarantine, never extend a lease. The round's OWN cleanup and the sweep's reclamation are different operations and conflating them broke reclamation entirely: `review_round_cleanup` gates on `review_round_all_terminal` (every recorded reviewer completed, timed out or confirmed stopped — proof is never the clock, since a reviewer whose deadline passed may still be running) while `review_round_reclaim`, the sweep's entry point, SKIPS that gate because for an abandoned round the expired lease IS the proof, and keeps the quarantine refusal. Putting the terminal gate inside the shared function meant an abandoned round could never be reclaimed, and silently, because the sweep's `|| true` swallowed the refusal. Path checks resolve symlinks on BOTH sides before comparing, and cleanup refuses — non-zero, nothing deleted — a path outside the `.review-rounds` parent, a symlink, `/`, and an escaping `..`. Finally, `review_round_dir_create` writes `.speccraft/.review-rounds/.gitignore` containing a single `*` line, idempotently and via same-dir temp + rename so two concurrent rounds cannot expose a truncated file: a rule added to the template's `.gitignore` would reach only repos that re-run `/speccraft:init`, leaving the whole installed base able to commit round payloads via `git add -A`, so protection arrives with the mechanism and is pinned against a checked-in copy of the pre-0054 template `.gitignore` rather than a shape the test constructs (spec 0054)
- Two outcomes mean exactly "the reviewer may still be running" — `failed codex-cancel-unconfirmed <job-id>` and `failed subagent-stop-failed <agent-id>` — and deleting the round dir then would remove a payload or an output path still in use, while keeping it conflicts with a cleanup rule that fires on every exit path. So the round gets a third terminal-ish state: the dir is RETAINED, its `lease` is left to expire on schedule (nothing extends it, because it is the `quarantine` record and not the lease that keeps the dir), `review_round_cleanup` REFUSES it non-zero with nothing deleted, and `review_round_sweep` on a quarantined dir whose lease expired but whose quarantine is unresolved REPORTS and does not delete, as one grep-able line per dir (`<dir>: quarantined <outcome> <id> lease-expired <iso-ts>`), so an orphaned reviewer is visible rather than silently swept. The record APPENDS one blank-line-separated block per reviewer, idempotently, first block first: written with a single-file overwrite it kept only the LAST agent id, so an operator lost the other handle and resolving the survivor would release the dir while the first reviewer might still be writing to it. Each block names the id, the outcome, the time, the reviewer's `mode` and — for `codex-plugin` — the CANONICAL RESOLVED companion root, which is required rather than bookkeeping: the probe has to run `status <job-id>` against the companion that OWNS the job, and with a per-agent `plugin_root` or two installations there is otherwise no way to pick it, so a record naming an id but no owner is unresolvable. Resolution is PER BLOCK and PER MODE, and only one mode is automatic: a `codex-plugin` block is resolved by a later `status <job-id> --json` confirming the job inactive, probed against the root RECORDED IN THAT BLOCK and never a re-resolved one (the install may have been removed or `plugin_root` dropped since), while a `subagent` block has no equivalent probe — the Agent tool exposes no termination query for an id whose `TaskStop` failed — and is released only by an operator removing it. Only resolved blocks are removed and the file is deleted only when none remain: a resolver that read the first block and deleted the whole file reclaimed the dir under a live job, and wiped a subagent block that no probe may resolve. The round itself still finalizes, with the quarantined reviewer's named failure counting toward NEITHER predicate. This is the only place cleanup is not unconditional, and no exit path may both quarantine and delete (spec 0054)
- Because the reviewer subagent writes its own `.out`, it is no longer strictly read-only, so the write surface is bounded on BOTH sides: the agent's instructions confine `Write` to `<round-dir>/<agent>.out`, and a post-round check compares `review_tree_snapshot` before and after, recording `failed subagent-wrote-files` on any change outside the round dir — the same treatment `touchedFiles` gets for `codex-plugin`, and a defect rather than a verdict. The snapshot is CONTENT, not an inventory: the sha256 of every tracked file outside the round dir PLUS the sha256 of every untracked regular file (enumerated `git ls-files --others -z`, per file and never `--directory`-collapsed), plus the path and type of every untracked non-regular entry. Four weaker mechanisms are rejected by name because each shipped and each left a hole: `git status --porcelain` text cannot carry the guarantee (editing an ALREADY-DIRTY tracked file leaves its ` M <path>` entry byte-identical, and adding a file beneath an already-untracked directory leaves the same collapsed `?? <dir>/` entry — both the common case during implementation); a path inventory misses a reviewer REWRITING THE BYTES of an existing untracked file while adding and removing nothing; `--exclude-standard` filters gitignored paths, so a write to `bin/` or `tools/bin/` would be invisible — and writing a built binary into `bin/` is the subject of a hard guardrail, making the most guardrail-relevant write exactly the invisible one; and `--directory` reinstates the collapsed-`??` hole. The snapshot must also check the ENUMERATION's exit status, not `sort`'s: outside a work tree it was empty AND successful, and two empty snapshots compare equal, so the check passed while detecting nothing. The excluded volatile set is a CLOSED, contract-level list of exactly four entries, excluded by name rather than as a side effect of a git flag — `.speccraft/.review-rounds/` (the whole tree, so the round dir, the `*` `.gitignore` SIBLING that a first round legitimately creates, `.building-*` dirs and concurrent rounds are all covered), `.claude/` (machine-local, and the orchestrating session writes permission allowlists anywhere under it mid-round), `.speccraft/state.json`, `tests/e2e/.logs/` — with a path merely PREFIXED by one of them (`.claudex/`) still counted, so the prefix rule cannot degrade into a substring match; widening the list is a spec change. The pre-round snapshot is taken AFTER the round dir is created, so setup is never in the diff and neither property is silently load-bearing. ATTRIBUTION is stated rather than left to an implementation, because a per-round snapshot pair yields no mutation timestamp and cannot place a write at an instant while the outcome is per agent: "active" means live at any point between the two snapshots, exactly ONE active subagent records the failure by name, and MORE than one records `failed subagent-wrote-files <unattributed>` against EVERY one of them. Failing all of them is deliberate and is the safe direction — the outcome counts toward neither predicate, so the round becomes incomplete rather than accepting a verdict from a reviewer that may have written out of bounds, and one misbehaving reviewer can nullify its concurrent peers because the alternative is trusting a verdict whose author cannot be cleared. A clean two-subagent round records neither failure, and a `codex-plugin` reviewer alongside a writing subagent is NOT swept up: the companion reports `touchedFiles` per job, so its writes are self-attested and that attestation is trusted — a tool that under-reports its own writes is a different threat model (a lying tool rather than an unattributable one) and is out of scope, as is a reviewer that lies about its digests. The attribution's own exit 2 must abort the round rather than be swallowed by a `|| true`: a round whose integrity check could not RUN must not finalize as though it passed (spec 0054)
- The round's recorded outcomes are a CLOSED vocabulary with a registered table, in two columns. Verdict and non-verdict tokens are `REVIEW_VERDICTS` / `REVIEW_AGREEING_VERDICTS` / `REVIEW_NON_VERDICTS`, read by `_review_outcome_kind` since spec 0035. The REASON column is what accreted unregistered — twelve `failed <reason>` tokens introduced across spec 0054's phases, each where it was needed, with nothing listing them, so nothing could tell a new reason from a TYPO of an existing one, and a typo'd reason is recorded, classified as a non-verdict, and reported to the operator as if it meant something. `REVIEW_FAILURE_REASONS` plus `review_failure_reason_known` now hold them (`codex-cancel-unconfirmed`, `codex-output-unparseable`, `codex-plugin-unavailable`, `codex-task-error`, `codex-wrote-files`, `duplicate-output`, `permission-denied`, `subagent-launch`, `subagent-no-output`, `subagent-permission-denied`, `subagent-stop-failed`, `subagent-wrote-files`), with `timeout late-completion` as the lateness outcome, and a source scan runs in BOTH directions: every reason the libs emit must be registered, and every registered reason must be emitted somewhere — a registered reason nothing emits is either dead vocabulary or a sign the emitting path was lost in a refactor, and either way an operator could never see it. Every one of these is a non-verdict counting toward neither round predicate (spec 0054)
