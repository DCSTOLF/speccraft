# Domain: ci-and-e2e

CI workflows and the e2e fixture harness: `run.sh` entrypoints/flags, per-language fixtures, devcontainer provisioning, environmental-failure annotation.

- An end-to-end test under `tests/e2e/` drives a single-crate Rust fixture through a full red→green→refactor cycle covering both inline and integration tests using the real `speccraft-guard` binary and a real `cargo` runner invocation (spec 0005)
- The devcontainer image and the CI e2e job provide a working Rust toolchain, and the e2e harness fails fast with `"cargo not found on PATH"` when `cargo` is absent (spec 0005)
- `tests/e2e/python_cycle.sh` is a hermetic Bash fixture (mktemp workdir, trap cleanup) that drives `speccraft-guard` via the Claude Code hook JSON protocol to assert the sibling-tier and `test_roots`-tier reject-then-allow flows, the no-test-anywhere rejection, and that editing a test file is always allowed (spec 0007)
- The Python e2e fixture is wired into `tests/e2e/run.sh` as a numbered step, exits 0 on success and 2 on any assertion failure, and requires only `python3` (no `pytest`) from the base image (spec 0007)
- `tests/e2e/run.sh --language-only` runs only the Rust and Python fixture scripts with no `claude -p` invocation and without requiring `ANTHROPIC_API_KEY`, exiting 0 on success and 2 on failure and skipping the lifecycle Go-module setup (spec 0008)
- `.github/workflows/ci.yml` includes an `e2e-language-only` job that runs on every push and pull_request, builds the devcontainer, executes `run.sh --language-only`, and never receives `ANTHROPIC_API_KEY` (spec 0008)
- The devcontainer provisions `~/.claude/session-env` as writable by the e2e job user, idempotently and surviving container rebuilds (spec 0008)
- The full-lifecycle e2e job annotates environmental `claude -p` failures with an `ENVIRONMENT_FAILURE:` prefix and a category tag (`credit_exhausted`, `auth`, or `transient_api`) while keeping a non-zero exit; non-environmental failures stay unannotated (spec 0008)
- `tests/e2e/javascript_cycle.sh` is a hermetic no-JS-runtime fixture driving `speccraft-guard` via hook JSON (with at least one `*.test.ts` assertion), wired into `run_language_fixtures()` (spec 0010)
- The `Hook tests (bats)` CI job installs Go and builds `speccraft-state`/`speccraft-guard` into `bin/` before running `bats tests/hooks/`, because the state-guard hook no-ops unless those binaries are on `PATH` (spec 0013)
- `tests/e2e/lib.sh` holds shared assertion helpers — `contains` (fixed-string) and `contains_regex` (extended-regex) — sourced by both `run.sh` and standalone fixtures so a fixture exercises the identical predicate as production; a `run_helper_unit_tests()` step runs these fixtures under the language-only tier (spec 0014)
- The e2e close-step verifies memory-keeper wrote a `history.md` ADR structurally via the anchored date-header regex `^## 20[0-9]{2}-[0-9]{2}-[0-9]{2}`, not by matching any feature keyword the model chose (spec 0014)
- The e2e `run_claude` helper passes `--model "${CLAUDE_MODEL:-claude-opus-4-8}"` so the model under test is explicitly pinned (not silently inherited from the account/CLI default) and is overridable per-run via the `CLAUDE_MODEL` env var (spec 0017)
- Every CI job that runs the test suite must BUILD the helper binaries and then STAMP `.binary-version` from `.claude-plugin/plugin.json` (never a literal, which stops matching at the next bump). `scripts/install-binaries.sh` compares that stamp against the plugin version and, on a mismatch, DOWNLOADS the last release and untars it over `bin/`; the stamp is gitignored, so it is absent on every fresh checkout. Without the stamp, any job or test reaching the SessionStart hook silently replaces freshly built binaries with the last RELEASED ones. This single bug produced three unrelated-looking symptoms — the Linux bats job, the macOS bats job, and the E2E job — and was as old as those tests, harmless only until one needed a subcommand newer than the last release (spec 0050)
- `tests/e2e/run.sh` must build the plugin binaries from source and stamp the version BEFORE the claude lifecycle, and ASSERT the built binary answers a post-release subcommand (exit ≠ 1, since an unknown subcommand exits 1 while `tasks-verify` with no path exits 2 by design). `--plugin-dir` loads HEAD's commands, hooks, agents and skills, but the binaries they shell out to were being downloaded from the last release — so the suite validated HEAD's markdown against RELEASE Go, and any command referencing a newer subcommand silently degraded. Nothing in this repo may test HEAD against a release; a test that provisions its own plugin root points `SPECCRAFT_RELEASE_BASE` somewhere unreachable instead (spec 0050)
- An agent-driven e2e step whose command contains a STOP-and-ask gate must tell the agent how to resolve it, or the run's outcome becomes non-deterministic. `/speccraft:spec:close` step 2 stops on `tasks-verify` violations and its bypass needs a literal token; with no guidance, whether the run passed depended on whether the `done:` predicates the agent authored at step [8/13] still matched the code it wrote at step [9/13]. Twice they did not — a test renamed by a refactor, a `grep -v` filter defeated by a path printed without `./` — and the agent CORRECTLY stopped, while the suite failed three steps downstream at `exists changelog.md`. The prompt now resolves it the way the command's own option (a) does (reconcile a stale LOCATOR, re-run, continue) and deliberately withholds the bypass token, since supplying it would stop exercising the gate at all; weakening a predicate stays forbidden, so the work must be done AND provable (spec 0050)
- `usage()` is the only self-description a built binary carries, so it is how a reader identifies WHICH build they hold — and a version that lags the code invites wrong inferences. A usage/dispatch parity test (every `case` in the top-level switch appears in `usage()`, bounded by the `default:` arm that prints "unknown subcommand", so the field-name switch below is excluded) found THREE subcommands undocumented at HEAD: `tasks-verify`, `review-commit`, `build-repair-log`. That mattered: a truncated usage dump was read as evidence of a stale release binary, but a CURRENT binary produced the same dump — the clobber was real, that particular evidence was not (spec 0050)
