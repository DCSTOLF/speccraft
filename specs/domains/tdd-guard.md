# Domain: tdd-guard

Core PreToolUse TDD enforcement: production-vs-test gating, sibling-test unlock, red-check accept/reject, and the override escape hatch.

- The `speccraft-guard pre-tool-use` TDD invariant (active spec required plus a sibling test edited in-session) applies to Python production files with the same block message used for Go (spec 0002)
- For Rust, the guard's red-check accepts an edit only when the runner reports `at_least_one_failed` for a failing test in the just-added set; `build_failed` is rejected as `"build failed"` and `all_passed` (ignored tests included) is rejected as `"no failing test observed"` (spec 0005)
- Before each guarded Rust edit the guard runs a pre-edit gate (`cargo check --tests` by default), short-circuited to zero `cargo`/`rustc` subprocesses when a whole-crate SHA-256 fingerprint of tracked files (`.rs` under `src/`,`tests/`,`examples/`,`benches/` plus `Cargo.toml`/`Cargo.lock`/toolchain configs, excluding `target/`) is unchanged in-session (spec 0005)
- The guard rejects Cargo workspaces (a root `Cargo.toml` with a `[workspace]` table) with a hard error naming the condition and referencing reserved follow-up spec 0006; only single-crate projects are supported (spec 0005)
- The Go/Python production guard consumes a single-shot override before the sibling-test check: when `override_pending` is set it allows exactly one edit and atomically clears the flag; the Rust dispatch path is not covered by override (spec 0009)
- The Go/Python/JS-TS production guard performs a real red-check, not a touch-check: it runs the just-added sibling test(s) through the runner primitive and allows the edit only when a test in the session's just-added set is observed to fail; `all_passed`, a failure outside the just-added set, an empty just-added set, timeout, and runner error all block. `build_failed` also blocks for Python and JS/TS, but **for Go it now routes to bounded build-repair mode** rather than refusing outright (specs 0018, 0048)
- Unlike Rust (which has a persisted baseline), Go/Python/JS-TS block on an empty just-added set rather than allowing it; introducing a brand-new production symbol whose just-added test cannot compile pre-edit remains the sanctioned `/speccraft:spec:override` case — though a RED authored as a data round-trip (literal JSON through a load/save boundary) keeps the package compiling and costs no override at all, and since spec 0048 a Go **build failure** no longer needs one either (specs 0018, 0048)
- When the configured or conventional runner for an in-scope language cannot be resolved or invoked, the guard fails closed with a "no test runner available" message and never falls back to the legacy touch-check (spec 0018)
- Writing files under `product/` or `design/` is exempt from the TDD PreToolUse guard (treated as a doc-zone like tests/docs/scratch), so authoring a brief or design doc is never blocked for lacking a failing test (spec 0022)
- The guard models post-edit content by the real `HookInput.ToolName`, not by payload shape: `Write` → post-edit content is `tool_input.content` (a new `Content` field; empty content = empty file, any `new_string` ignored), `Edit` → a single `old_string→new_string` replacement preserved even when `old_string` is empty, and any other tool → post-edit equals pre-edit (no modeled change, no red-candidates) (spec 0031)
- A Write-authored test file therefore registers its red-candidates exactly as an Edit-authored one, closing the blind spot that forced overrides while implementing 0030 (spec 0031)
- `applyEdit` also models `MultiEdit` (apply each `edits[]` `{old_string→new_string}` in array order as a first-occurrence replacement on the running content, so a later entry sees an earlier one's output; an empty `old_string` entry is skipped, an absent target is a silent no-op) and `NotebookEdit` (`new_source` is the whole post-edit content, empty string included), so a RED test authored via either tool captures its red-candidates override-free exactly as via Write/Edit; the `default:` branch stays the unchanged-content fallback for the next unmodeled tool (spec 0032)
- For **Go only**, an adapter result of `build_failed` no longer refuses the edit: the guard applies the proposed edit in memory via `applyEdit` and probes that content with `go test -overlay … -run '^$' -count=1 ./...` (one command — `go build` alone misses a broken `_test.go`, and `go build -o <dir> ./...` additionally fails outright on a library-only module). Four outcomes, in order: no prober for the language → today's byte-identical refusal; probe cannot complete → BLOCK naming both the build error and the probe failure, because a probe that cannot answer must never read as clean; overlay clean → the edit REPAIRS the break, so clear the attestation and allow silently; overlay still broken → allow, but record first (spec 0048)
- Build-repair admissions are bounded at `buildRepairMaxEdits` = 10 per session, enforced INSIDE the same atomic `RecordBuildRepair` operation that appends the entry and opens the attestation — the only placement where "recorded before allowed" is race-free, since two guard invocations checking outside it could each see 9 and both append. The budget derives solely from the log's length: the attestation carries no counter (one there could diverge), and a clean probe clears the attestation but NEVER the log, so break → spend → repair → break cannot refund spent budget. Only `ResetSession` resets it. The 11th admission blocks, naming `/speccraft:spec:override` (spec 0048)
- Relatedness is deliberately NOT inferred — a break in file A is routinely repaired in file B — so an unrelated Go edit IS admitted while the tree is broken. The claim is correspondingly narrow: at most 10 such edits can exist per session, every one is recorded before it is allowed, and `speccraft-state build-repair-log` surfaces them at `/speccraft:spec:close` step 2. That report is informational BY CONTRACT (always exit 0, even on a read error), because a report that could fail the close would make honest multi-step repair look like failure and the rational response would be to avoid repair mode (spec 0048)
- Red candidates are recomputed as `postIDs − red_baseline[file]`, never as `postIDs − preIDs`. The per-file baseline is captured FIRST-TOUCH-ONLY per session under one lock and one save, so an edit adding no new `func Test…` recomputes the SAME candidate set instead of clearing it, while a genuine deletion still shrinks it. First-touch is tested with `_, ok :=` rather than a length check: a brand-new test file whose baseline is legitimately empty has still been touched, and re-deriving it on the next edit would reintroduce the clobber (spec 0048)
- A failed red-candidate capture BLOCKS the test-file edit — the one case where a test-file edit is refused, and deliberate. The guard runs in PreToolUse, so a refusal leaves the file byte-unchanged on disk and the natural retry re-captures from identical content; allow-and-mark-poisoned cannot recover, because once the edit lands the disk holds the new test and any later capture baselines it away (spec 0048)
- One canonical `NormalizeStateKey` keys red candidates, baselines and build-repair log paths (abs → `EvalSymlinks` of the deepest EXISTING ancestor → rejoin the non-existent tail → `Clean`, so a file created in-session still gets a key), applied on BOTH sides of the sibling lookup. Two normalizers that disagree register a candidate under a key the lookup can never see — state.json plainly shows it while every production edit is refused. **Spec 0050 is that failure, exactly as predicted, shipped anyway**: `SetRedCandidates` stored the caller's spelling verbatim while `siblingRedCheck` read through the normalizer, so the guard answered "No test was added this session" for a session that had added one. The single-DEFINITION assertion that pinned this could not catch it — one definition existing does not prove every writer CALLS it — so the writer normalizes internally (a documented caller-normalizes contract is unenforceable) and the invariant is pinned at the WRITER through a symlinked ancestor, asymmetrically. Only visible where some ancestor is a symlink, i.e. every macOS `t.TempDir()` under `/var/folders`: 25 guard tests failed there and passed on Linux, and `TMPDIR` pointed at a symlink reproduces all 25 on Linux, which is the general technique for this class. Still outstanding: `TrackEdit` keys `edited_test_files`/`edited_prod_files` with a bare `filepath.Abs`, so spec 0048's "every state key this package writes" is not yet literally true — nothing reads those through the normalizer today, so either honour the claim or narrow it (spec 0048, corrected by spec 0050)
- The gated write-tool set is declared once as `var gatedWriteTools` and pinned against its four consumers — `applyEdit`'s switch, both `hooks.json` matchers, and `GATED_TOOLS` in `hooks/pre-tool-use.sh`. Extending some but not all fails silently in the worst way: the hook never fires for the new tool, so every guard rule quietly stops applying to edits made with it. Corollary: a file written by SHELL rather than a gated tool never reaches the guard at all, so a test authored that way registers zero red candidates (spec 0048)
- Run the Go suite under a symlinked `TMPDIR` when touching path-keyed state: `TMPDIR=<dir reached through a symlink> go test ./...` reproduced all 25 macOS-only guard failures on Linux, byte-for-byte the same set. macOS `t.TempDir()` returns `/var/folders/…`, a symlink to `/private/var/folders/…`, so the divergence is not about macOS at all — it is about whether any ancestor is a symlink, equally true of a Linux checkout under a symlinked home. This is the general local repro for "passes on Linux, fails on macOS" path bugs, and cheap enough to run before pushing rather than after a red run (spec 0050)
- A test must compute a state key with the same function production WRITES it with. Guard tests read `red_candidates` via a bare `filepath.Abs`, which was equivalent only while no ancestor was a symlink; the mismatch hid a real writer-side defect for as long as CI ran on Linux alone. Assert asymmetrically — build the expected key from the resolved path with NO call to the normalizer — so a regression that turns the normalizer into a no-op cannot satisfy the assertion (spec 0050)
- When dogfooding, the guard enforcing the invariant may be the INSTALLED plugin, not this repo's. Spec 0050 spent 2 overrides against a stated budget of 0, both because the cached 1.11.0 plugin predates spec 0048: one hit defect A (its pre-edit build probe refused the edit that repairs the build) and one hit defect B (a comment-only test-file edit cleared that file's red candidates, so a present, failing, just-added test was invisible to it). Neither bypassed a real RED and HEAD's guard would have allowed both. An override log entry should therefore name WHICH guard refused the edit, because "the installed plugin is older than the fix" and "the invariant was bypassed" are different facts (spec 0050)
