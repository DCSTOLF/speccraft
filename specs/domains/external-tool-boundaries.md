# Domain: external-tool-boundaries

Speccraft defers routing for external tools it does not own (code-intel/call-graph) to the user's environment; no brand endorsements in model-loaded, template, or human-facing surfaces.

- Speccraft defers all code-intelligence routing (call-graph / symbol-search tool choice) to whatever tool the user has installed; its skills, commands, and templates do not enumerate or express a preference for a specific tool (spec 0011)
- Templates under `templates/speccraft/` stay stack-agnostic and name no specific external enforcement tool; a code-intel tool may appear only as a neutral example ("such as CodeGraphContext"), never as a recommendation (spec 0011)
- Prescriptive routing prose toward an unowned external tool ("prefer it over grep/find", "use its tools", "the recommended way", "should install ... alongside speccraft") is disallowed in every speccraft surface including human-facing `README.md` and overview docs; neutral labels such as "Recommended companions" are retained (spec 0016)
- The `/speccraft:spec:review` payload is TIERED by a fixed table keyed on identity, never on size: the spec content plus `.speccraft/guardrails.md` and `.speccraft/index.md` are INLINE (pasted verbatim, because guardrails must be unmissable), while `.speccraft/architecture.md` and `.speccraft/conventions.md` are REFERENCE (a repo-relative path, a byte size, and a `^##`/`^###` heading index in file order). Classification resolves against `speccraft-state find-root` and matches the full repo-relative `.speccraft/<name>`, never the trailing basename, so `vendor/other/.speccraft/conventions.md` and a spec document sharing the basename are errors; any path outside both tables is an error, `.speccraft/history.md` included, since nothing is added to what a reviewer sees (spec 0052)
- Heading extraction is one fence-aware `LC_ALL=C awk` pass emitting `^## ` and `^### ` in file order: a fence opens on three or more backticks or tildes (info string allowed, indentation allowed) and closes only on the same character at the same or greater length, an unclosed fence suppresses headings to EOF, and a trailing CR is stripped so a CRLF checkout yields an identical record. It uses NO regex interval expression, because mawk does not implement them and matches nothing silently while the identical spelling works under GNU `grep -E` (spec 0052)
- `commands/spec/review.lib.sh` is the SOLE byte-producing owner for review dispatch, and `review_compose_payload` is the single composer for every round a review command can run — the full spec round, the spec-0035 scoped `--diff` round, and (spec 0054) the `arch:review` design round, the `pm:review` brief round and the `spec:review-code` frozen-diff round — because a second composer would mean a second answer to "what was sent" and the budget can only measure one. The per-round wording comes from an optional `--label <text>` whose default is byte-identical to the original literal, which is what kept 0052's composer tests passing unedited. It emits the payload to STDOUT only, rejects a reference-tier file passed in the inline position, errors on a named-but-missing reference file, emits the reference section with an explicit "none" marker for an empty set, and writes exactly one other file: the `--digest-out` sidecar carrying `<sha256>  <repo-relative-path>` lines, which exists so the composition-time digests never enter the payload. Every branch's output begins with a NON-WHITESPACE byte and ends with EXACTLY ONE `\n` (`_review_normalize_payload_ends`, asserted per branch including inputs that end with no newline and with several) — the invariant that makes the Codex companion's `prompt.trim()` a provable no-op, since it can then remove exactly that final newline and nothing else; the budget measures the untrimmed artifact, an upper bound on what is sent. Each agent is composed and materialized into its OWN artifact path: one shared `payload.md` dispatched to every reviewer while a later step validated a per-agent path meant a reviewer could return the right digest for the bytes it was given and still fail attestation (spec 0052, amended by spec 0054)
- Reviewer payloads are bounded BEFORE dispatch by `review_budget_check <bytes> <input-mode>`, which echoes `ok` or `refuse:<reason>` and exits 0 in both cases because a refusal is data, not a shell failure: `REVIEW_MAX_ARGV_BYTES` (65536, the field-reported ~70 KB argv working limit rounded down to a power of two, and a conservative policy floor rather than a guarantee of process creation) applies to `argv` AND `acp` since ACP is invoked as `acpx <agent> <prompt>` and is therefore argv transport; `REVIEW_MAX_PAYLOAD_BYTES` (262144, the next power of two above the largest payload ever observed to complete against both shipped CLIs) applies to every mode; `stdin`, `file`, and an absent `input` key take the payload limit only; an unrecognised mode is an error so the next argv transport cannot slip in exempt; and `refuse:payload-limit` wins deterministically when both bite. The second argument is the TRANSPORT, which since spec 0054 is no longer the same thing as the registry's dispatch `mode`: `review_agent_transport <toml> <agent>` maps an agent to it and returns `file` for both `codex-plugin` (the payload goes to the companion as `--prompt-file`) and `subagent` (the reviewer is handed a path), so an 80 KB payload is `ok` for them while `cli` + `argv` is `refuse:argv-limit`. A caller that reads one where the other belongs is a defect, not a style point — `/speccraft:spec:review` passed `input` as the dispatch mode, which silently skipped the subagent-only digest check and produced the wrong permission token — so the two reads are separate and separately named. `getconf ARG_MAX` probing is rejected — it would make the refusal boundary vary by machine (spec 0052, amended by spec 0054)
- An over-budget agent is refused PER AGENT, before dispatch, with a remedy specific to the limit that bit: `review_refusal_message` names the agent, its input mode, the measured bytes, the numeric limit from the RUNTIME effective value (so the diagnostic cannot disagree with the behavior when an override is in play), the inline files ranked by size, and either the literal `input = "stdin"` migration plus `.speccraft/agents.toml` for an argv-limit refusal or compaction/a shorter spec for a payload-limit one — never the migration line for the latter, since stdin does not help there. `REVIEW_MAX_ARGV_BYTES`/`REVIEW_MAX_PAYLOAD_BYTES` are accepted only as base-10 integers >= `REVIEW_MIN_LIMIT_BYTES` (1024); any other value warns on stderr naming the variable and proceeds with the compiled default rather than aborting the review (spec 0052)
- The payload is materialized EXACTLY ONCE and measured as dispatched, and since spec 0054 a review round materializes it in a PERSISTENT directory rather than a trap-cleaned temp dir: `review_round_tmpdir` (0700 + a cleanup trap on `EXIT HUP INT TERM` installed immediately — it sets a variable rather than echoing a path, because a command substitution would install the trap in a subshell that exits at once; `SIGKILL` is a stated uncoverable boundary) survives as a helper with its spec-0052 tests unedited, but NO review command may use it: a `subagent` reviewer is dispatched in a LATER tool call and would find a trap-cleaned payload gone, which made running one structurally impossible, and a payload under `$TMPDIR` is outside the project's permission scope besides. The four review commands use `.speccraft/.review-rounds/<kind>-<id>-<unix-ts>-<rand>` instead, and a negative grep over `commands/spec/review.md` pins the supersession so the ephemeral dir cannot return by habit. Everything else stands and is now PER AGENT: `review_materialize_payload` redirects the composer stdout once into a single 0600 artifact and REFUSES one that already exists; that same artifact is what gets piped to stdin, passed via `--file`, read for argv, or handed to the Codex companion as `--prompt-file` (asserted inode-equal with `test -ef`, never a copy); `review_dispatch_bytes` uses a byte-preserving read because reading into a variable would strip trailing newlines at the file-to-argv boundary; `review_payload_representable` rejects a NUL byte (POSIX argv cannot carry one) or invalid UTF-8, naming which failed; and no debug or convenience copy may be written anywhere — a cached full prompt would restore the unbounded artifact by a side channel while the budget check still reported success (spec 0052, amended by spec 0054)
- Reference-tier reads are ATTESTED, not assumed: the reviewer returns `reference_access: [{path, sha256}]` for every reference path and reports unreadable ones in `reference_access_failures: [{path, reason}]`, with the expected digests withheld from the payload — a digest cannot be produced without reading the bytes, whereas an in-prompt sentinel would prove only that the reviewer read the prompt. A `subagent`-mode response additionally carries `payload_sha256` of the payload FILE it was handed by path (absent → `attestation-failed missing-payload-digest`, wrong → `attestation-failed payload-digest-mismatch`), and a reviewer refused a read or a hash reports `permission_denied: <tool>`, which maps to the mode-scoped outcome `failed subagent-permission-denied` (fix: the command's `allowed-tools`) rather than the CLI-scoped `permission-denied` (fix: that agent's `cmd`) — never to a generic `attestation-failed`, the uninformative outcome 0052 removed elsewhere. `review_validate_reference_access` is exact (every expected path present exactly once, no unknown path, every digest matching, no duplicate, an empty failures list) and tolerant of how the CLIs actually wrap YAML, and `review_attestation_outcome` maps its `invalid:<reason>` to the recorded `attestation-failed <reason>` — an unmapped token must not be recorded, and a substring assertion on the reason is not a test of that mapping. EVERY dispatchable template (`review.md`, `re-review.md`, `review-code.md`, `arch-review.md`, `pm-review.md`) documents the `reference_access` block it will be parsed by, and each is round-tripped through the real parser by test: spec 0054's own review round 3 went INERT on format rather than access — both reviewers read the files and computed correct digests, then invented shapes (a YAML map `<path>: <digest>`; `- path: X, sha256: Y` on one line) because `re-review.md` showed no schema and never named `reference_access`, so a scoped round could not attest at all. A verdict failing any arm counts toward NEITHER round predicate, the same rule as a timeout, and is reported in its own category so a chronically failing reviewer is diagnosable. The guarantee is deliberately the weaker one: it proves a process with filesystem access at the dispatched cwd obtained the bytes, NOT that the model reasoned over them, and nothing proves a reviewer reports its own digests honestly (spec 0052, amended by spec 0054)
- Reviewer capability is a dispatch contract with three halves. Subagents declare `Read` in `agents/*.md` frontmatter. External CLIs carry a `reference_read` flag in `.speccraft/agents.toml` that is OPT-OUT — an absent key means `true`, because every already-initialized repo lacks it and requiring it would have made every configured reviewer ineligible on the first `git pull`; only an explicit `reference_read = false` refuses reference-tier dispatch, with a named message. A `subagent`-mode reviewer declares `Write` as well, because it writes its own `<round-dir>/<agent>.out` and the orchestrator only reads that file: `review_subagent_preflight` refuses a custom `subagent_type` whose frontmatter lacks `Write` with `failed subagent-launch missing-write-tool` BEFORE any Agent launch (rather than a silent empty verdict), warns at review time on one declaring `Edit` (it can modify files in place, which the post-round tree check catches only after the fact), and refuses any non-`speccraft:` plugin qualifier with `failed subagent-launch unsupported-subagent-plugin <type>` — stripping the qualifier vetted `otherplugin:reviewer` against *speccraft's* `agents/reviewer.md` while the Agent tool would launch a different plugin's agent, and another plugin's definitions cannot be read, so the only honest options were a named refusal or a check of the wrong file. The frontmatter reader that answers "does it declare `Write`" must accept an UNINDENTED block-list item (legal YAML), must not let a nested block's `tools:` key shadow the top-level one, and must print its value once — all three were preflight bypasses. Every half is invoked with cwd set to the root `speccraft-state find-root` reports for the active spec (in a workspace, the member repo), since reference-tier paths are only resolvable there (spec 0052, amended by spec 0054)
- `aux-delegator` is a PURE DISPATCHER for review rounds: given a precomposed payload artifact, an input mode and a cwd, it sends those bytes unmodified and must NOT re-prefix the review template, re-inline context files, or write another copy for `input = "file"` (it passes the artifact itself). Left composing, a round would compose twice and the bytes the budget measured would not be the bytes dispatched — the materialize-once rule broken by the component furthest from the check. Its `implement` and `analyze` modes are unchanged, asserted byte-identical rather than described as such. Its FIRST act, before it composes anything, is `review_require_delegatable_mode`: a `codex-plugin` or `subagent` entry is refused by name because there is no `cmd` to shell out to, and a refusal after composing would already have spent the round. The task kind it takes is `task_mode`, renamed from `mode` because two different things were called "mode" — the task kind and the registry's dispatch mode — and passing one where the other belonged was a live defect in `/speccraft:spec:review`; the agent file states the distinction where both appear, and the golden that pins the agent's doc was updated with the rename. `templates/speccraft/agents.toml` ships `input = "stdin"` on its three `cli` entries ONLY — `input` is a named error on `codex-plugin` and `subagent`, and the `acp` entry carries none because ACP is argv by construction — and ships exactly ONE reviewer enabled, the `subagent`, the only one that needs nothing installed, with every other entry `enabled = false` EXPLICITLY and the reason written beside it. `enabled` is opt-out, which is exactly how three CLI entries came to be enabled in the shipped template (an absent key means true and nobody ever wrote one), and an enabled reviewer whose binary is absent does not degrade gracefully: its dispatch fails, `responses_complete` is false, and no `review.md` is written at all even if another reviewer approved. Repos already initialized own their copy and are never rewritten, so the argv refusal and the named per-agent failure are their migration nudge (spec 0052, amended by spec 0054)
- `.speccraft/agents.toml`'s `mode` is the DISPATCH mode — how a reviewer is reached — and has exactly four values, `cli | acp | codex-plugin | subagent` (`REVIEW_VALID_MODES`). `cli` and `acp` shell out to a standalone binary; `codex-plugin` reaches the Codex plugin's own runtime (`scripts/codex-companion.mjs`), which carries the user's Codex auth, config, job tracking and thread persistence that a `codex exec` shell-out bypasses; `subagent` reaches the orchestrating Claude Code session's own Agent tool, which needs no binary, no auth and no argv/stdin transport. An OMITTED `mode` normalizes to `cli` (today's behaviour, unchanged); an explicitly empty or unrecognised value, case variants (`Subagent`, `CLI`) included, is a named error at registry load that names the agent and the four valid values. Per-mode optional fields: `model` / `effort` (`none|minimal|low|medium|high|xhigh`) / `plugin_root` for `codex-plugin`; `subagent_type` (default `speccraft:reviewer`) and `model` (`opus|sonnet|haiku|fable|inherit`, default `inherit`) for `subagent`. STRICT KEYS APPLY TO THE NEW MODES ONLY: on a `codex-plugin` or `subagent` entry, `cmd`, `input`, `acp_agent` and the other new mode's fields are named errors, while `cli` and `acp` entries keep permissive decoding so an unknown key such as `install_hint` still loads and no already-initialized host registry stops loading on a `git pull` — the opt-out convention for host-owned config. `reference_read`, `strengths` and `enabled` apply to every mode. The rule has TWO readers that must agree — the Go loader (`tools/internal/delegate`) and the shell reader `review_agent_mode` — and they are held to ONE fixture corpus, `tests/hooks/fixtures/review-dispatch/registries/`: a DIRECTORY of per-case files rather than a single registry, because `LoadConfig` fails the whole file on the first bad entry while `review_agent_mode` is per-agent, so one shared file could not drive both (spec 0054)
- A `codex-plugin` reviewer resolves to a companion ROOT before anything else: `plugin_root` if set, else the entry for `codex@openai-codex` in `~/.claude/plugins/installed_plugins.json` — the `scope: "local"` entry whose `projectPath` equals the repo root, else the `scope: "user"` entry's `installPath` — and the root must contain `scripts/codex-companion.mjs`. Both sides of that `projectPath` comparison are CANONICALIZED in shell, one entry at a time: canonicalizing the repo root and handing it to `jq` to match a raw `.projectPath` is a string comparison between two spellings of one directory, so a local-scope entry could never be selected on macOS (`$TMPDIR` under `/var/folders/…`, `/var` a symlink to `/private/var`) and resolution fell through to the USER-scope companion SILENTLY — the round went to a different installation than the operator configured. The supported-interface check is version + readiness and NEVER help text: 1.0.6's real `printUsage` omits `--prompt-file`, `--cwd` and `--json` even though `handleTask` accepts all three, so a help-text probe fails CLOSED against the one install this targets, and a fixture holding that verbatim capture asserts such a companion still resolves successfully — the test exists so reintroducing the probe fails loudly. The version comes from the resolution path that produced the root, because an explicit `plugin_root` may have no `installed_plugins.json` entry at all and sourcing the version only from that file would leave a valid explicit root permanently `unknown-version` with no satisfiable configuration: root from `installed_plugins.json` → that entry's `version`; root from an explicit `plugin_root` → the companion-owned `<root>/.claude-plugin/plugin.json`; a root in both reads `installed_plugins.json`, so one path yields one version. Supported starts at 1.0.6 and is forward-compatible above it. The failure reason is exactly ONE of `not-installed`, `companion-missing`, `unsupported-companion <version>`, `unknown-version` — siblings, never concatenated, so the named error is reproducible and greppable. `review_codex_preflight` then runs `node <root>/scripts/codex-companion.mjs setup --json` as the availability and auth gate, mapping `ready: false` to `not-ready <reason>` and never to `codex-output-unparseable`; it is MEMOIZED per canonical resolved root, not per round, with the symlink resolution happening BEFORE the memo key is formed — `plugin_root` is per-agent, so two entries in one round can resolve to different installations, versions or auth states, and preflighting once per round would establish readiness for one and assume it for the other (spec 0054)
- `codex-plugin` dispatch uses the companion's JOB lifecycle, not a foreground turn: `node <root>/scripts/codex-companion.mjs task --background --fresh --json --prompt-file <payload> --cwd <repo-root> [--model …] [--effort …]`, never `--write`, `--resume` or `--resume-last`, with the payload passed as the round's own materialized artifact by path. A foreground `task` cannot be cancelled — the companion spawns the Codex broker DETACHED and `unref`'d, closing its socket only clears ownership while the turn keeps running, and only `companion cancel <job-id>` reaches `interruptAppServerTurn` — so killing the companion's process group would prove the local caller stopped, not that the reviewer stopped. The adapter therefore takes the job id from the launch output, polls `status <job-id> --json` on a fixed interval until a terminal state or `review_timeout_s`, retrieves `result <job-id> --json`, and on deadline expiry runs `cancel <job-id> --json` and CONFIRMS it with one further `status` before recording `<agent> timeout`; a cancel that does not confirm is `failed codex-cancel-unconfirmed <job-id>`, which names the job so an operator can finish it by hand, because a reviewer that may still be running is never reported as merely timed out. Each individual companion invocation (`setup`, `task`, `status`, `result`, `cancel`) additionally runs under a portable deadline wrapper, `review_with_deadline <seconds> <cmd…>` (returning 124 on expiry and leaving no child alive — macOS has no `timeout(1)`), so a hung companion process cannot stall the round, while expiry of the JOB deadline goes through cancel-and-confirm rather than a process-group kill. Plugin not installed, root unresolvable, version outside the supported range, `node` absent or `setup --json` reporting `ready: false` → `<agent> failed codex-plugin-unavailable <reason>` plus a message pointing at `/codex:setup`, NEVER a fallback to `codex exec`; the other reviewers still run. Background jobs are in scope only for this adapter's own dispatch: speccraft starts, polls, collects and cancels only jobs it launched, and never adopts, resumes or reports on a Codex job it did not start (spec 0054)
- The companion's reviewed response is read from the BACKGROUND shape and that path only: `review_parse_codex_task_output <file> <exit-status>` extracts `.storedJob.result.rawOutput`, with `.storedJob.result.status` the numeric completion status (`0` success, `1` otherwise) and `.storedJob.result.touchedFiles` the files written. Two different fields are named `status` at different depths with different types — `.job.status` / `.storedJob.status` are strings (`queued`, `running`, `completed`, `failed`, `cancelled`) while `.storedJob.result.status` is a NUMBER — so checking `== "completed"` at the wrong depth looks plausible and is wrong, and checking it against the launch payload (whose `status` is the non-terminal string `"queued"`) is wrong twice. Success is all three of a zero exit code, `result.status === 0`, and a non-empty `result.rawOutput`. The classification is TOTAL over (exit status × JSON validity × field contents) so no combination is left to implementer judgement: non-zero exit is `failed codex-task-error` whether or not the stdout parses — INCLUDING stdout that is valid success-shaped JSON, the quadrant most easily got wrong, because a companion that printed a well-formed result and then exited non-zero has had a transport failure and a transport failure never becomes a verdict; zero exit with a non-zero `result.status`, an empty or absent `result.rawOutput`, invalid JSON, or valid JSON carrying a FLAT top-level `rawOutput` and no `.storedJob.result` is `failed codex-output-unparseable`, with no fallback to the flat foreground shape, so a caller that forgot `--background` cannot silently produce a verdict; and a non-empty `result.touchedFiles` is `failed codex-wrote-files` and WINS over every other row, even with a valid verdict in `result.rawOutput`, because a read-only reviewer that wrote is a defect, never a verdict. The exit status is an EXPLICIT parameter rather than ambient, since the table cannot be implemented without it. Who holds which bytes is pinned too: the parser is given the stdout file and the exit status and nothing else, and never reads stderr; the CALLER captures stderr to its own file during the invocation and attaches the excerpt to the recorded outcome on a `codex-task-error`. The extracted response then goes through the same verdict parse and `review_validate_reference_access` as any other reviewer. The interface facts are pinned by fixtures with stated provenance — the `printUsage` capture is verbatim from the installed 1.0.6, the success payload is derived field-for-field from its source (line references in `tests/hooks/fixtures/review-dispatch/codex/INTERFACE-1.0.6.md`) rather than from a live run — so drift fails a test (spec 0054)
- Bash cannot call the Agent tool, so a `subagent` reviewer is dispatched by the ORCHESTRATING SESSION, not by `aux-delegator`: `review_dispatch_agent` routes `cli`/`acp` to `review_dispatch_payload` and `codex-plugin` to the companion, and returns a named error for `subagent` ("subagent reviewers are dispatched by the orchestrating session") so a bash path never silently drops one. The reviewer receives the payload PATH, never pasted content, reads it, reports `payload_sha256` alongside the reference digests, and WRITES ITS OWN output to `<round-dir>/<agent>.out`, which the orchestrator only reads — having the orchestrator transcribe the Agent tool result would make "verbatim" an instruction rather than a mechanism, since the orchestrator is itself a model and a paraphrase would still pass the hash-compare rule, which catches duplication but not rewording; a grep-level negative asserts the runbook contains no transcription instruction. A missing or empty `.out` after the agent returns is `failed subagent-no-output`, never an empty verdict. `agents/reviewer.md` (`speccraft:reviewer`) declares tools exactly `Read, Grep, Glob, Bash(shasum:*), Bash(sha256sum:*), Write` with `model: inherit`, NO `Edit` (so it cannot modify a file in place) and no bare `Bash` — the scoping is mechanical rather than prose, because declaring bare `Bash` while asking the body to please only run `shasum` leaves exactly the declared-vs-permitted gap the post-round tree check exists to compensate for; the body confines `Write` to that single path, which frontmatter cannot express, which is why the tree check backs it. `speccraft:reviewer` is a REVIEWER — once per `subagent` entry, during dispatch — and `speccraft:cross-reviewer` is the SYNTHESIZER — once per round, after dispatch, reading every `.out` and writing the consolidated `review.md`; each file states the contrast in its first lines and a test asserts neither describes itself with the other's role, so one is never dispatched in the other's place. Registry `model = opus|sonnet|haiku|fable` is passed explicitly (all four are accepted by the Agent tool, `fable` included, so the accept list and the dispatch surface agree), while `inherit` or absent passes no model and resolves to the parent session's — which works ONLY because `reviewer.md` declares `model: inherit`; for a custom `subagent_type` an omitted model follows that agent's own frontmatter and is recorded as `requested: inherit (per <agent> definition)`. The timeout protocol is seven stated steps, because an under-specified one left a round unable to tell a stopped reviewer from a running one: launch in the background for an agent id; record that id and an ABSOLUTE deadline in the round dir so it survives across tool calls; wait for completion notifications rather than polling; at the deadline stop any incomplete reviewer with `TaskStop` and record `<agent> timeout`, or `failed subagent-stop-failed <agent-id>` if the stop errors; IGNORE a reviewer that completes after its deadline and record `<agent> timeout late-completion`, judged against a completion stamp written when the notification arrived and never against the clock at collection time (judging at collection made one slow reviewer discard every other verdict in the round); partial output is never a verdict; and cleanup runs only once every reviewer is PROVEN terminal. The four review commands' `allowed-tools` therefore list `Agent`, `TaskStop`, `Bash(shasum:*)` and `Bash(sha256sum:*)` (plus `Write` for `review-code`), with `TaskStop` load-bearing rather than decorative: it is the only way the protocol can stop a background reviewer (spec 0054)
- `codex-plugin` and `subagent` are REVIEW-DISPATCH adapters, and the registry is shared, so `/speccraft:spec:delegate` and `aux-delegator` refuse them explicitly through one helper (`review_require_delegatable_mode`) with the contracted text `unsupported-mode: <mode> is a review-only dispatch mode (used by spec:review, arch:review, pm:review, spec:review-code); spec:delegate supports cli and acp`. Without the refusal both consumers would improvise — `spec:delegate` accepts any registered agent, and `aux-delegator` reads `cmd`/`input` fields that neither new mode has — which is how a delegation silently becomes a no-op or an unquoted shell-out. The refusal is a PRECONDITION before any dispatch or prompt composition, so nothing is partially executed, and it is asserted by a stub that records invocation; `cli` and `acp` delegation through both consumers is unchanged, with the existing delegate tests passing unedited. The refusal text is the contract and not a paraphrase of it — a paraphrase shipped once, with its own test agreeing with it while both disagreed with the stated string. This is a guardrail, not a roadmap: making the review-only modes work for implement-mode delegation stays out of scope, and the error text promises nothing (spec 0054)
- A reviewer's VENDOR is derived from the registry entry and never guessed from its output: `review_agent_vendor <toml> <agent>` returns `anthropic|openai|unknown` by an EXACT match on the basename of argv[0] of the entry's `cmd` — nothing else — with `subagent` mode ⇒ `anthropic` and `codex-plugin` mode ⇒ `openai` by construction. So `claude` and `/usr/local/bin/claude` are `anthropic` (basename only, flags ignored), `codex` is `openai`, and `claude-p`, `claude_wrapper.sh` and `/opt/wrappers/opus` are `unknown`: no substring matching and no first-token prefix heuristics, because a wrong vendor label is worse than an absent one for a value whose only job is to be believed, and a user who wraps a binary can state the vendor by naming the real one in `cmd`. Reading `cmd` for this purpose goes through `review_agent_cmd`, not the raw field reader, since every real registry is ARRAY-form and the raw text of a TOML array is not a command (spec 0054)
- The invariant tiering guarantees is the PAYLOAD bound, not the argv one. Spec 0052 measured its live corpus at 4.03x and asserted the tiered composition fits under `REVIEW_MAX_ARGV_BYTES` — an empirical property of the corpus at that moment, asserted as though invariant, with a test comment claiming a new archive entry could not falsify it. Archiving spec 0054 falsified it: its own `spec.md` is 85,338 B, more than double the previous largest, so the tiered composition for the largest archived spec is ~104 KB — over the 65,536 argv limit and comfortably under the 262,144 payload one, at a still-healthy 2.86x. Nothing in the design broke, because tiering never promised every spec fits argv; it promised the payload is BOUNDED and an over-budget agent is refused BEFORE dispatch with a reason naming the limit that bit. So the corpus arm now asserts the payload bound, and additionally pins the arm that makes an argv overflow safe and which that corpus never exercised: an over-argv tiered payload yields `refuse:argv-limit` on `argv` and `ok` on `stdin`. The shipped default reviewer is unaffected either way — a `subagent` uses `file` transport (spec 0054)
